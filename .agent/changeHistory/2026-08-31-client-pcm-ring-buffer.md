# 客户端 PCM 环形缓冲与声音连续性优化

- 日期：2026-08-31
- 目标：消除画面冻结修复后出现的声音断续，同时保持原采样质量、声音事件频率和低延迟。
- 仓库：`O:\java\games\CS2D-MultiplayerUDP_Client`
- 分支：`main`
- 修改前基线：`2168dc9813f2df8a564c188d9b305de1a4a8c89c`（`fix: eliminate periodic client frame freezes`）
- 当前实现状态：已作为后续设备批量写入优化前的 Git 基线保存。

## 诊断依据

- 最新 115 秒 JFR 中最长 `jdk.SafepointBegin` 只有 `3.36ms`，之前的数秒级全局暂停已经消失。
- 最新客户端日志不再出现周期性数秒画面冻结，但 PCM 声音存在断续。
- 日志显示声音请求数与已混音数基本一致、事件队列通常为 `0～3`，说明声音事件没有大量丢失。
- 同期活跃声音达到约 `80～124` 路，但混音计算仍能完成；高并发可能导致响度饱和，不是本次周期性音频空洞的直接原因。
- JFR 中 PCM 线程共有 179 个原生样本，其中 160 个位于 `DirectAudioDevice.nWrite()`，169 个位于设备写入调用链；`nAvailable` 已为 0。
- 旧实现把 256 帧块按 `5.333ms` 的 Java 定时器逐块提交，并在迟到后丢弃追赶节拍。Windows 调度或设备写入稍有延迟就可能让设备缓冲吃空，造成声音断续。

## 文件变更

### `src/main/java/cs2d/client/PcmAudioMixer.java`

- 行数：新增 186 行，删除 42 行。
- 删除依赖 `LockSupport.parkNanos()` 的单块固定时钟提交模式。
- 将声音管线拆成固定的 `CS2D-PCM-Mixer` 与 `CS2D-PCM-Writer` 两个守护线程。
- 混音线程提前生成 PCM；写入线程由 `SourceDataLine` 自然背压连续喂给声卡，不再依赖 Windows 每 5.333ms 精确唤醒。
- 新增三个可复用 PCM 块：最多两个已就绪块，另一个由混音或写入线程持有；运行期间不分配新的音频块。
- 声卡端请求两个 256 帧块，Java 端预缓冲两个块，目标总延迟约 21ms，并覆盖常见 Windows 调度抖动。
- 启动时先完成两个 PCM 块的预缓冲再启动声卡播放，避免冷启动欠载。
- 保持 `48,000Hz / 16-bit / stereo / 256-frame`、原始 PCM 内容、增益、并发 voice 和声音事件频率不变。
- `stopAll()` 改为异步清空 voice、待写块和设备缓冲，不会误中断并关闭整个音频系统。
- 音频线程异常时会协调关闭另一线程和设备；客户端关闭时安全中断两个线程并回收缓冲块。
- 新增欠载次数、当前/最低缓冲水位、写入次数、平均/最大写入耗时和超过两个块周期的迟写次数统计。

## 手动验证、限制与回退

- 必须完全退出并重启客户端，旧 JVM 不会加载新的双线程音频管线。
- 实战日志中正常目标是：`欠载 0`、`缓冲` 多数为 `1～2块`、`min` 不长期为 0，平均写入约一个 256 帧周期。
- 如果声音仍表现为爆裂或浑浊，但欠载保持 0，应继续分析 80～124 路并发 voice 的混合饱和，而不是继续增加缓冲。
- Java Sound 最终仍需在独立写入线程调用原生 `nWrite()`；最新 JFR 已证明该调用存在时 Safepoint 仍保持毫秒级。
- 如需回退，可从基线 `2168dc9` 恢复本轮三个源码/测试文件并删除本记录；用户设置不受影响。
