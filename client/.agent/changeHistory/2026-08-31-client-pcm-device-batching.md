# 客户端 PCM 设备批量写入修复

- 日期：2026-08-31
- 目标：修复枪声有节奏地慢放、PCM 样本长期积压的问题，使 Windows Java Sound 输出重新达到实时 48kHz。
- 仓库：`O:\java\games\CS2D-MultiplayerUDP_Client`
- 分支：`main`
- 修改前基线：`5920fad0efbe16ffccb8f547beb1b21f558c87af`（`chore: snapshot before pcm output batching`）
- 当前实现状态：工作区未提交，等待实机听感与输出速率复测。

## 诊断依据

- 用户听到枪声呈现有节奏的慢速“砰……砰……砰……”，属于整条 PCM 时间轴变慢，不是普通爆音。
- 256 帧在 48kHz 下只代表 `5.333ms` 音频，但 Windows `SourceDataLine.write()` 实际平均每块耗时约 `17～40ms`。
- 单次设备写入最大耗时约 `321～396ms`，每个统计窗口有约 `11～23` 次迟写。
- 理论上两秒应输出约 375 个 256 帧块，实测多数窗口仅完成约 `49～116` 次小块写入。
- 活跃 voice 从约 25 路持续堆积至 140～147 路，证明旧声音的样本游标推进过慢，新声音又继续加入。
- 环形缓冲多数保持两块且欠载为 0，说明生产端混音足够快；瓶颈是 Windows 原生输出对 5.333ms 小写入的固定等待开销。

## 文件变更

### `src/main/java/cs2d/client/PcmAudioMixer.java`

- 行数：新增 52 行，删除 22 行。
- 保持每 256 帧执行一次 voice 混音，不改变声音事件时间精度。
- 将连续四个 256 帧 PCM 块按原字节顺序复制成一个 1024 帧设备批次。
- 每个设备批次代表 `21.333ms` 音频，以匹配 Windows DirectAudio 的实际调度粒度并摊薄原生写入固定开销。
- Java 端启动预缓冲改为四个 256 帧块，固定块池改为五块；写入线程复制后立即回收小块，混音线程可在原生写入期间并行准备下一批。
- 设备端申请一个 1024 帧批次大小的缓冲，并在启动日志中同时输出 requested 与 actual 字节数。
- 运行期间只复用一个设备批次数组和固定 PCM 块，不增加每批对象分配。
- 迟写阈值从两个 256 帧周期调整为两个 1024 帧批次周期，避免把正常约 21ms 的设备背压误判为迟写。
- 新增实际输出帧数统计，并按统计窗口墙钟时间计算 `outputRealtimePercent`；该指标直接反映是否持续达到 48kHz。
- 新增 `copyPcmBlock(...)`，以边界校验后的 `System.arraycopy` 保证批次拼接顺序和样本内容不变。

## 手动验证、限制与回退

- 必须彻底退出并重启客户端，旧 JVM 不会加载新的设备批次。
- 启动日志应显示 `batch=1024 frames`，并给出设备实际缓冲字节数。
- 稳定实战窗口的理想日志是：`实时` 接近 100%、两秒约 90～100 批、约 96,000 帧、欠载 0。
- 平均设备写入耗时接近 21ms 属于正常背压；最大值可以偶发升高，但实时输出比例不应长期显著低于 100%。
- 若实时输出仍显著不足，说明当前 Java Sound/DirectAudio 设备实现不适合低延迟游戏混音，应改用专用 WASAPI 输出层，而不是继续增加 Java 缓冲。
